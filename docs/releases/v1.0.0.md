# Hibalag AI v1.0.0

Status: draft release candidate. Do not publish until the reviewed AI change is
merged, deployed, verified, and the owner approves the annotated tag and GitHub
Release.

## Independent application

- Primary: [hibalag-ai.pages.dev](https://hibalag-ai.pages.dev)
- Secondary rollback:
  [hibalag-ai.doodstecson.workers.dev](https://hibalag-ai.doodstecson.workers.dev)
- GitHub `doodstecsonhere/hibalag-ai` is authoritative.
- The retained Lovable site remains separately published but is not a runtime or
  source dependency of either Cloudflare application.

The release includes reliable guest and authenticated conversation state,
ownership-isolated Supabase persistence, schedule browsing, deterministic
fallback, and installable PWA assets. Google OAuth returns to the initiating
Pages, Worker, or retained Lovable origin.

## Database, Auth, and recovery

The reviewed production migrations enforce matching thread/message ownership,
restrict external execution of the privileged event-trigger function, preserve
its `postgres` ownership and enabled trigger, and add the covering ownership
index. Auth and cross-user RLS tests used disposable fictional identities.

The encrypted Supabase archive, DPAPI-protected recovery key, and protected
final database credential remain outside OneDrive. The newest archive's
recorded SHA-256 was reverified on 2026-08-29 without decrypting it or displaying
records. Database recovery is separate from code or deployment rollback.

## Online AI and deterministic fallback

- Provider: Cloudflare Workers AI.
- Model: `@cf/meta/llama-3.1-8b-instruct-fp8`.
- Prompt: the existing Hibalag system prompt and schedule-grounding rules,
  unchanged by this correction.
- Bindings: `AI`, `AI_QUOTA`, and `AI_ENABLED`.
- Server-only secret: `AI_RATE_LIMIT_PEPPER`.
- Emergency switch: `AI_ENABLED=false` disables inference and fails closed.

Signed-in Supabase bearer tokens are validated before account quotas are used.
Guest/IP and user identifiers are HMAC-pseudonymized before the shared SQLite
Durable Object receives them. The application does not intentionally log raw
identities, IP addresses, tokens, prompts, conversations, responses, schedule
text, or secrets.

Limits are 5 requests per minute and 20 per UTC day for each signed-in user, 3
per minute and 10 per UTC day for each guest/IP identity, and 20 accepted
requests per UTC day globally across Pages and Worker. The model has a 32,000
token context window; the route additionally limits the request body, history,
individual messages, schedule context, output, and execution time.

Cloudflare lists 13,778 Neurons per million input tokens and 26,128 per million
output tokens for the model. A conservative calculation using 32,000 input
tokens and the full 800-token output is about 461.8 Neurons per request or about
9,236 Neurons for 20 requests. The application ceiling assumes Hibalag is the
only Workers AI consumer in the account. Cloudflare's account-wide 10,000
Neuron daily free allocation remains the final fail-closed limit; no paid
fallback or AI Gateway unified billing is permitted.

When AI is disabled, exhausted, unavailable, malformed, or timed out while the
browser is online, the application identifies live AI as unavailable and offers
the deterministic assistant. A genuinely offline browser uses cached schedules
and deterministic offline responses.

## Privacy and terms

Cloudflare receives only the bounded prompt material required for inference.
Hibalag does not intentionally send email addresses, raw Supabase user IDs, raw
IP addresses, credentials, or private database records to the model. See the
[Cloudflare Workers AI data-usage policy](https://developers.cloudflare.com/workers-ai/platform/data-usage/)
and [Meta Llama 3.1 model card](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/MODEL_CARD.md).

Built with Llama.

## Rollback

Code: revert the faulty shared commit through a reviewed pull request; never
rewrite published history.

Deployment: set `AI_ENABLED=false`, then restore the previous known-good Pages
deployment or Worker version. Keep the secondary Worker available while Pages
is repaired. Removing bindings or the unused Durable Object is a separate
external action.

Database structure: use the migration-specific rollback under
`docs/preservation`, then repeat Auth, RLS, constraint, trigger, and advisor
checks. Data recovery: verify the encrypted archive and restore into an isolated
compatible environment before any separately approved production recovery.

A Git or Cloudflare rollback does not reverse a database migration or restore
changed or deleted records.
