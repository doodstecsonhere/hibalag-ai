privileged event-trigger function. Production RLS, constraints, grants,
function ownership, trigger state, index, and application queries were
verified. Isolated Auth lifecycle and cross-user tests used disposable
fictional accounts.

Before a destructive database action, verify the encrypted backup under
`C:\Code\Backups\hibalag-ai`, outside OneDrive, and its DPAPI-protected key. The
latest archive is `supabase-20260827-121023.7z`, recorded SHA-256
`7988B21FC0A36D6975BE4DF696ECC976D6E7C4C612EF78CF9E46F41DB25F2FD1`.

recorded schema, Auth metadata, policies, triggers, and counts. Never publish

## AI, PWA, cost, and privacy

The provider, model, and prompt are unchanged. Live AI is disabled on both
deployments because `LOVABLE_API_KEY` is absent; no AI request was made during
readiness checks. Schedule browsing and deterministic chat fallback remain
available. The manifest, service worker, Workbox runtime, cached reload, and
required static assets were verified.

Both deployments remain zero-dollar with no card, trial, paid feature, overage
setting, secret, custom domain, or DNS change. Pages Functions and the Worker
share the account-level Workers Free quota. No production records or secrets
are included in this release.

## Known limitations

- Production Pages hard-offline behavior relies on identical-package local and
  Worker evidence because blocking system networking would be disruptive.
- Leaked-password protection remains disabled in Supabase.
- Full production email-based Auth journeys remain manual.
- Application canonical metadata and `robots.txt` still reference Lovable.
- Managed-service recovery also needs dashboard configuration, Auth settings,
  storage, and secret inventories; a database archive alone is insufficient.

## Rollback

Deployment: use the unchanged Worker URL if Pages is unhealthy, then rebuild
and redeploy a reviewed known-good commit only after approval.

Code: create a revert commit and reviewed pull request; never rewrite shared
history. Deployment of the revert is a separate approval.

Database structure: verify the encrypted backup, use the migration-specific
rollback documented under `docs/preservation`, and repeat RLS/Auth/advisor
checks. Data recovery: verify the archive hash, restore into an isolated
compatible PostgreSQL environment first, then restore production only under a
separate disaster-recovery approval.

A Git revert or Cloudflare rollback does not reverse a database migration or
restore records.
